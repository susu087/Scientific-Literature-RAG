BM25
inline_acl = 引文改写 + ACL 来源
inline_nonacl = 引文改写 + 非 ACL 来源
manual_acl = ACL 作者手写
manual_iclr = ICLR 作者手写
Recall:召回率，所有正确答案，找回了多少
Hit:前K个结果，是否至少出现了一个正确答案
MRR：如果第一个正确答案排在第 r位，那么得分是：=1/r
Recall@10 = 0.5149
Recall@50 = 0.6668
Recall@100 = 0.7362
Hit@10 = 0.5260
Hit@100 = 0.7487
MRR@10 = 0.3522
MRR@100 = 0.3610
在 LitSearch 数据集上，基于 title_abstract 字段构建 BM25 稀疏检索索引，并对 597 条查询进行评测。实验结果显示，BM25 在该基准上的 Recall@10、Recall@50、Recall@100 分别为 0.5149、0.6668、0.7362，MRR@10 为 0.3522。结果表明，BM25 作为传统关键词匹配方法，能够召回一定比例的相关文献，但在复杂科研文献检索场景下，其排序质量与召回能力仍存在明显局限。LitSearch 论文也报告，最优 dense retriever 在 Recall@5 上显著优于 BM25。

import sentence_transformers
import numpy as np
from typing import List, Any
from sklearn.metrics.pairwise import cosine_similarity
from eval.retrieval.kv_store import KVStore
from eval.retrieval.kv_store import TextType
from utils import utils
class E5(KVStore):
def init(self, index_name: str, model_path: str = "intfloat/e5-large-v2"):
super().init(index_name, 'e5')
self.model_path = model_path
self._model = sentence_transformers.SentenceTransformer(model_path, device="cuda", cache_folder=utils.get_cache_dir()).bfloat16()
def _format_text(self, text: str, type: TextType) -> str:
if type == TextType.KEY:
text = "passage: " + text
elif type == TextType.QUERY:
text = "query: " + text
else:
raise ValueError("Invalid TextType")
return text
def _encode_batch(self, texts: List[str], type: TextType, show_progress_bar: bool = True) -> List[Any]:
texts = [self._format_text(text, type) for text in texts]
return self._model.encode(texts, batch_size=256, normalize_embeddings=True, show_progress_bar=show_progress_bar).astype(np.float16)
def _query(self, encoded_query: Any, n: int) -> List[int]:
cosine_similarities = cosine_similarity([encoded_query], self.encoded_keys)[0]
top_indices = cosine_similarities.argsort()[-n:][::-1]
return top_indices
def load(self, path: str):
super().load(path)
self._model = sentence_transformers.SentenceTransformer(self.model_path, device="cuda", cache_folder=utils.get_cache_dir())
return self

进一步来看，E5 在 Recall@100 上相较 BM25 的提升幅度小于 Recall@10 和 MRR@10 的提升幅度，这表明 BM25 在较大的候选范围内仍具有一定召回能力，但 E5 的优势主要体现在“前排结果质量”上。这一点对于实际系统应用尤为重要，因为用户通常更关注前若干条检索结果的相关性与可用性。因此，从用户体验和系统实用性角度看，E5 相比 BM25 更适合作为后续学术检索增强系统中的主检索模块。

4.X.1 实验目的
为进一步分析不同检索方法在不同类型查询上的适用性，本文在 LitSearch 数据集上分别统计了 BM25 与 E5 在不同 query_set 上的检索表现。数据集中的查询分为四类：inline_acl、inline_nonacl、manual_acl 和 manual_iclr。其中，inline_* 类查询主要由论文正文中的引用语境改写而来，通常语义较复杂、自然语言特征更强；manual_* 类查询则由人工编写，通常主题更明确、关键词更集中。通过分组对比，可以进一步观察稀疏检索与稠密检索在不同查询场景下的优势与局限。

4.X.3 结果分析
从表 4-X 可以看出，E5 对不同类型查询的提升并不均匀，其优势主要体现在 inline_acl 和 inline_nonacl 两类查询上。相较于 BM25，E5 在 inline_acl 上的 Recall@10 从 0.4531 提升至 0.5398，Hit@10 从 0.4898 提升至 0.5918，MRR@10 从 0.2829 提升至 0.3876，说明 E5 不仅能够召回更多相关文献，还能更有效地将正确结果排在前列。
在 inline_nonacl 上，E5 的提升更为明显。其 Recall@10 从 0.4111 提升到 0.5415，Recall@50 从 0.5553 提升到 0.7055，Recall@100 从 0.6621 提升到 0.7609，MRR@10 也从 0.2648 提升到 0.3546。该结果表明，对于这类由论文上下文改写而来的复杂自然语言查询，稠密检索模型能够更好地捕捉查询与文献之间的语义关系，因此在召回能力和排序质量上均显著优于 BM25。
相比之下，在 manual_acl 上，E5 相对于 BM25 的优势较为有限。E5 在 Recall@10 与 MRR@10 上仍有小幅提升，但在 Recall@50、Recall@100 以及 Hit@100 上略低于 BM25。这说明对于人工编写且关键词较明确的查询，BM25 依赖词面匹配的机制仍然具有较强竞争力，而语义检索的提升空间相对较小。
在 manual_iclr 上，BM25 甚至略优于 E5。具体来看，BM25 的 Recall@10 为 0.7363，而 E5 为 0.6813；BM25 的 MRR@10 为 0.5283，也高于 E5 的 0.5085。造成这一现象的一个合理解释是，manual_iclr 类查询通常主题明确、术语集中，与目标文献的标题和摘要在词项层面存在较高重合度，因此 BM25 已能取得较好的表现，而 E5 的语义表示优势在这类查询上没有得到充分体现。
综合来看，E5 的主要优势在于改善 BM25 在复杂语义查询上的不足，尤其是对 inline_* 类查询的检索性能提升较为显著；而对于术语明确、词面重合度较高的人工查询，BM25 仍然保持较强的基线能力。这一结果说明，在科学文献检索任务中，稠密检索并非在所有场景下都绝对优于稀疏检索，但其在处理复杂自然语言查询时具有更强的适应性和更高的实际应用价值。
4.X.4 小结
通过对不同 query_set 的分组对比实验可以看出，E5 相较于 BM25 的优势主要体现在语义更复杂、表达更自然的 inline_acl 和 inline_nonacl 查询上，而在 manual_acl 和 manual_iclr 这类关键词更集中、词面匹配更强的查询上，BM25 仍然具有较强竞争力。该结果表明，科学文献检索任务具有明显的查询类型差异，后续系统设计中可考虑结合稀疏检索与稠密检索的优势，以进一步提升整体检索性能。

X.X 实验结果与分析
为验证不同检索方法在 LitSearch 数据集上的效果，本文依次对 BM25、E5 稠密检索 以及 E5 + Reranking 三种方案进行了实验，并采用 Recall@10、Recall@50、Recall@100、Hit@10、Hit@100、MRR@10 和 MRR@100 作为评价指标。其中，Recall 用于衡量相关文献的召回能力，Hit 用于衡量前若干结果中是否至少命中一篇相关文献，MRR 则重点反映首篇相关文献在结果列表中的排名位置。因此，Recall 和 Hit 更能体现系统的覆盖能力，而 MRR 更能体现检索结果在前排位置上的排序质量。
X.X.1 BM25 与 E5 的总体结果对比
首先，对 BM25 和 E5 两种基础检索方法进行整体比较。实验结果表明，E5 在大多数指标上均优于 BM25，说明语义表示能力更强的稠密检索方法在 LitSearch 任务上具有明显优势。
具体来看，BM25 的 Recall@10、Recall@50 和 Recall@100 分别为 0.5149、0.6668 和 0.7362，Hit@10 和 Hit@100 分别为 0.5260 和 0.7487，MRR@10 和 MRR@100 分别为 0.3522 和 0.3610。相比之下，E5 的 Recall@10、Recall@50 和 Recall@100 分别提升到 0.5827、0.7386 和 0.7748，Hit@10 和 Hit@100 提升到 0.5963 和 0.7889，MRR@10 和 MRR@100 则提升到 0.4116 和 0.4199。
从提升幅度看，E5 相比 BM25 在 Recall@10 上提升了 0.0678，在 Hit@10 上提升了 0.0703，在 MRR@10 上提升了 0.0594。这说明 E5 不仅能够召回更多相关文献，而且能够将相关文献排到更靠前的位置。总体而言，E5 在 LitSearch 数据集上表现出了比 BM25 更强的检索能力，说明基于预训练语义表示的稠密检索方法能够更好地捕捉查询与文献之间的深层语义相关性。
X.X.2 不同 query_set 下 BM25 与 E5 的分组结果分析
为了进一步分析不同类型查询对检索效果的影响，本文按照数据集中的 query_set 对结果进行了分组统计，包括 inline_acl、inline_nonacl、manual_acl 和 manual_iclr 四类。
从分组结果来看，E5 的优势并不是完全均匀分布的，而是主要体现在 inline_acl 和 inline_nonacl 两类查询上。对于 inline_acl，BM25 的 Recall@10 为 0.4531，MRR@10 为 0.2829，而 E5 分别提升到 0.5398 和 0.3876；对于 inline_nonacl，BM25 的 Recall@10 和 MRR@10 分别为 0.4111 和 0.2648，E5 则提升到 0.5415 和 0.3546。尤其是在 inline_nonacl 这一组中，E5 在 Recall@10、Recall@50、Recall@100 以及 MRR 指标上均有较明显提升，说明对于这类来源更复杂、表述更自由的查询，稠密检索能够更好地建模查询与文献之间的语义匹配关系。
相比之下，在 manual_acl 这一组中，E5 相较 BM25 仍有一定提升，但优势没有前两组明显。具体而言，manual_acl 上 E5 的 Recall@10 从 0.5935 提升到 0.6194，MRR@10 从 0.4352 提升到 0.4627，但在 Recall@50、Recall@100 和 Hit@100 上反而略低于 BM25。这表明对于人工构造且表达较规范的查询，BM25 仍然能够利用关键词匹配获得较强的效果，而 E5 的语义优势在这一组中没有完全转化为更高的中后段召回。
最值得注意的是 manual_iclr 这一组。在该组中，BM25 的 Recall@10、Hit@10 和 MRR@10 分别达到 0.7363、0.7363 和 0.5283，而 E5 对应指标分别为 0.6813、0.6813 和 0.5085，均略低于 BM25。这说明在部分人工构造且主题表达非常集中的查询场景下，关键词匹配方法仍然具有较强竞争力。换言之，manual_iclr 组的查询可能具有更明确的术语特征，使得 BM25 能够凭借词项重合度快速锁定相关文献，而 E5 的语义表示优势没有充分发挥出来。
综合分组结果可以看出，E5 相比 BM25 的主要收益集中在更复杂、更依赖语义理解的查询上，特别是 inline_acl 和 inline_nonacl 两类。对于关键词高度集中、表述较规范的人工查询，BM25 仍然保留一定优势，尤其是在 manual_iclr 这一组中表现较为突出。这说明不同检索方法在不同类型查询上的适用性存在差异，也说明在后续实验中引入第二阶段重排具有必要性。
X.X.3 E5 + Reranking 的总体结果分析
在 E5 初始召回结果的基础上，本文进一步引入本地 CrossEncoder reranker，对前 20 个候选文献进行重排，以验证第二阶段精排是否能够提升前排检索质量。
实验结果表明，加入 reranking 后，系统的前排表现得到了明显改善。总体上，Recall@10 从 0.5827 提升到 0.6053，Hit@10 从 0.5963 提升到 0.6198，MRR@10 从 0.4116 提升到 0.4637，MRR@100 从 0.4199 提升到 0.4706。与此同时，Recall@50、Recall@100 和 Hit@100 分别保持在 0.7386、0.7748 和 0.7889，与原始 E5 基本一致。
这一结果表明，reranking 的主要作用不是扩大召回范围，而是对 E5 已经召回到前 20 的候选文献进行更细粒度的相关性排序，从而将真正相关的文献推到结果列表更靠前的位置。特别是 MRR@10 提升了 0.0522，MRR@100 提升了 0.0508，这说明首篇相关文献的平均排名明显前移，对用户实际检索体验具有较强意义。对于文献检索任务而言，用户往往更加关注前几条结果，因此这种前排排序质量的提升具有较高应用价值。
X.X.4 E5 + Reranking 的分组结果分析
进一步按照 query_set 对 reranking 的效果进行分析，可以发现其对不同类型查询的影响存在明显差异。
对于 inline_acl，加入 reranking 后 Recall@10 基本保持不变，从 0.5398 变化为 0.5395，Hit@10 也保持在 0.5918 不变；但 MRR@10 从 0.3876 提升到 0.4210，MRR@100 从 0.3923 提升到 0.4262。这说明在该组中，reranker 并没有显著改变相关文献是否进入前 10 的结果，但能够进一步优化相关文献在前列中的相对顺序。
对于 inline_nonacl，现象与 inline_acl 类似。Recall@10 从 0.5415 略微下降到 0.5395，Hit@10 保持在 0.5534 不变，但 MRR@10 从 0.3546 显著提升到 0.4077，MRR@100 从 0.3636 提升到 0.4173。说明对于这类更自由、更复杂的 inline 查询，CrossEncoder 能够在候选集内部进行更准确的细粒度相关性判断，从而将真正相关的文献进一步提前。
相比之下，manual_acl 和 manual_iclr 两组在 reranking 后表现出更明显、也更全面的提升。对于 manual_acl，Recall@10 从 0.6194 提升到 0.6710，Hit@10 也同步从 0.6194 提升到 0.6710，MRR@10 从 0.4627 提升到 0.4959，MRR@100 从 0.4706 提升到 0.4995。这表明对于表达较规范、意图相对明确的人工构造查询，reranker 不仅能改善排序位置，还能将更多相关文献提前到前 10 个结果中。
manual_iclr 的提升则最为显著。该组中 Recall@10 从 0.6813 提升到 0.7473，Hit@10 同样从 0.6813 提升到 0.7473，MRR@10 从 0.5085 大幅提升到 0.6107，MRR@100 也从 0.5196 提升到 0.6177。特别是 MRR@10 的增幅达到 0.1022，说明在该类查询上，CrossEncoder 的细粒度匹配能力得到了充分体现。结合前文可知，manual_iclr 是 BM25 相对 E5 更占优势的一组，而在加入 reranking 后，该组的前排排序性能反而出现了最显著的提升，说明第二阶段重排在这类表达集中、主题清晰的查询上具有很强的纠偏和增强作用。
总体而言，reranking 对 inline_acl 和 inline_nonacl 的主要收益体现在 MRR 的提升上，即优化前列结果的具体排序；而对 manual_acl 和 manual_iclr，其不仅改善了 MRR，还明显提高了 Recall@10 和 Hit@10。这说明对于表达更规范、语义更明确的查询，CrossEncoder 更容易学习并利用查询与文献之间的细粒度匹配信号，从而获得更全面的提升。
X.X.5 本节小结
综合以上实验结果可以得出以下结论。首先，在基础检索阶段，E5 整体上显著优于 BM25，说明稠密检索方法在 LitSearch 任务中具备更强的语义建模能力。其次，这种优势主要体现在 inline_acl 和 inline_nonacl 等更复杂、更依赖语义理解的查询上；对于 manual_iclr 这类关键词特征更集中的查询，BM25 仍然具有一定竞争力。最后，在 E5 初始召回的基础上引入 CrossEncoder reranking 后，系统的前排检索质量得到进一步提升，尤其是在 MRR@10 和 MRR@100 上表现突出，说明第二阶段重排能够有效优化候选文献的排序顺序。
因此，从整体实验结果来看，“E5 负责初始召回，CrossEncoder 负责候选重排” 的两阶段检索框架在 LitSearch 数据集上取得了最优效果。该结果说明，第一阶段稠密检索能够提供较强的候选覆盖能力，而第二阶段重排能够进一步提升前排结果质量，两者结合比单独使用任一方法都更适合该任务。

X.X 实验设置
为系统评估不同检索方法在 LitSearch 任务上的表现，本文围绕 BM25、E5 稠密检索以及 E5 + CrossEncoder 重排 三种方案开展实验，并在统一的数据集、评价指标和实验环境下进行对比分析。
X.X.1 数据集与任务说明
本文实验使用 LitSearch 数据集。该数据集包含 597 条查询（query） 和 64183 篇候选文献。每条查询都对应一组标注的相关文献，用于评估检索系统返回结果与真实相关文献之间的一致程度。
从任务形式上看，LitSearch 属于典型的学术文献检索任务：给定一个查询，系统需要从候选文献库中返回按相关性排序的结果列表。本文的实验重点是比较不同方法在该任务上的检索效果，尤其关注系统能否将相关文献排在结果列表前部。
此外，数据集中的查询还带有 query_set 标记，本文进一步按照该字段对结果进行分组分析。具体包括以下四类：
inline_acl
inline_nonacl
manual_acl
manual_iclr
其中，前两类可视为更贴近真实引用或上下文场景的查询，后两类则属于人工构造查询。通过分组实验，可以更细致地观察不同方法在不同查询类型上的适用性与优劣差异。
X.X.2 对比方法
本文共设置三类检索方案进行比较。
（1）BM25
BM25 作为经典的稀疏检索方法，以词项匹配为核心，通过统计词频和逆文档频率衡量查询与文献之间的相关性。本文首先基于 LitSearch 语料构建 BM25 索引，并据此生成检索结果，作为传统关键词匹配方法的基线模型。
（2）E5 稠密检索
E5 属于基于预训练语义表示的稠密检索方法。与 BM25 依赖显式词项重合不同，E5 通过将查询和文献映射到同一向量空间，利用向量相似度完成检索，因此更适合捕捉查询与文献之间的深层语义相关性。本文在项目原有实现基础上完成了 E5 检索实验，并在 GPU 环境下构建索引与生成检索结果。
（3）E5 + CrossEncoder Reranking
在 E5 初始召回结果的基础上，本文进一步引入第二阶段重排（reranking）机制。具体做法是：先利用 E5 获得候选文献列表，再使用本地 CrossEncoder 模型对前若干个候选文献进行精排，从而进一步优化前排排序质量。实验中采用的重排模型为 BAAI/bge-reranker-base，并对 E5 召回结果前 20 个候选文献进行重排；第 21 位及之后的候选文献保持原始 E5 顺序不变。这样既能保留 E5 的整体召回能力，又能利用 CrossEncoder 的细粒度匹配能力改善前排结果质量。
X.X.3 索引内容与实验流程
为保证不同方法之间的可比性，本文在检索阶段统一采用文献的 标题（title）和摘要（abstract） 作为索引内容。对于每条查询，系统输出一个按相关性排序的候选文献列表，再与该查询对应的真实相关文献集合进行比较。
整体实验流程如下：
使用 BM25 或 E5 对全部候选文献进行初始检索；
生成按相关性排序的检索结果列表；
在 E5 的结果基础上，对前 20 个候选文献使用 CrossEncoder 进行第二阶段重排；
基于标注的相关文献集合计算各项检索指标；
在总体层面和 query_set 分组层面分别对实验结果进行分析。
该流程对应了一个典型的两阶段检索框架，即“第一阶段负责候选召回，第二阶段负责候选精排”。
X.X.4 评价指标
为了从不同角度评估检索方法的效果，本文采用了 Recall、Hit 和 MRR 三类指标，并分别在不同截断位置上进行计算。
（1）Recall@K
Recall@K 用于衡量在前 K 个检索结果中召回了多少真实相关文献，其计算公式为：
[
Recall@K = \frac{|Relevant \cap TopK|}{|Relevant|}
]
其中，Relevant 表示该查询对应的真实相关文献集合，TopK 表示系统返回的前 K 个结果。Recall 越高，说明系统的召回能力越强。
（2）Hit@K
Hit@K 用于判断前 K 个结果中是否至少包含一篇相关文献。如果命中，则记为 1，否则记为 0。对全部查询求平均后，可以反映系统在前 K 个结果中“至少找对一次”的概率。
（3）MRR@K
MRR（Mean Reciprocal Rank）用于衡量首篇相关文献在结果列表中的位置，其计算方式为首个相关结果排名倒数的平均值：
[
MRR@K = \frac{1}{N} \sum_{i=1}^{N} \frac{1}{rank_i}
]
其中，(rank_i) 表示第 (i) 条查询的首篇相关文献在前 K 个结果中的排名；若前 K 个结果中不存在相关文献，则该项记为 0。MRR 越高，说明相关文献越靠近结果列表前部。
本文具体报告以下指标：
Recall@10、Recall@50、Recall@100
Hit@10、Hit@100
MRR@10、MRR@100
其中，Recall 与 Hit 更侧重于考察检索系统的覆盖能力，而 MRR 更关注用户实际最敏感的前排排序质量。

X.X.6 实现细节
在实现层面，本文对项目代码进行了必要的适配与调整，以保证实验能够在当前硬件和软件环境下稳定运行。
对于 E5 检索实验，原实现中包含 bfloat16 精度设置，但该设置在当前环境下会导致运行错误，因此实验中将其移除，并使用标准浮点计算完成编码。与此同时，为避免显存占用过高，E5 的推理批大小最终设置为 32。在该设置下，能够稳定完成语料编码、索引构建与检索实验。
对于 reranking 实验，项目原始代码依赖 Azure OpenAI 接口，无法直接满足本文实验需求。为此，本文保留了原有的检索与结果写回流程，并新增本地重排脚本，将原先基于 API 的排序模块替换为本地 CrossEncoder 推理。具体而言，实验采用 BAAI/bge-reranker-base 作为重排模型，推理设备设置为 GPU，批大小设置为 4，最大输入长度设置为 512。实验中仅对 E5 检索结果前 20 个候选文献进行重排，以降低计算开销并突出第二阶段排序对前排结果的优化作用。
在结果评估方面，本文实现了独立的指标计算脚本，对总体结果和不同 query_set 分组结果分别进行统计分析，从而保证实验结果可复现、可对比。

 重排深度消融实验
为了进一步分析第二阶段重排范围对检索性能的影响，本文在 E5 初始召回结果的基础上，分别设置了 Rerank(top20) 和 Rerank(top50) 两种重排深度进行对比实验。其中，Rerank(top20) 表示仅对 E5 返回结果中的前 20 个候选文献进行 CrossEncoder 精排；Rerank(top50) 则表示将重排范围扩大到前 50 个候选文献，而第 51 位及之后的结果保持原始 E5 顺序不变。通过这一设置，可以观察随着重排候选范围扩大，系统前排检索质量是否会持续提升。
从总体结果来看，随着重排深度从 top20 扩展到 top50，系统性能进一步提高。原始 E5 的 Recall@10、Hit@10 和 MRR@10 分别为 0.5827、0.5963 和 0.4116；在采用 Rerank(top20) 后，这些指标分别提升至 0.6053、0.6198 和 0.4637；进一步扩大到 Rerank(top50) 后，Recall@10、Hit@10 和 MRR@10 又进一步提升到 0.6288、0.6399 和 0.4683。与此同时，MRR@100 也从 0.4199 依次提升到 0.4706 和 0.4747。相比之下，Recall@50、Recall@100 和 Hit@100 在三种设置下基本保持不变。这说明扩大重排范围并不会改变系统整体的召回覆盖范围，但能够进一步改善前排排序质量。
从增量角度看，Rerank(top20) 相比原始 E5 已经带来了较大提升，尤其是在 MRR 指标上最为明显；而 Rerank(top50) 虽然继续优于 Rerank(top20)，但提升幅度已经明显缩小。例如，Recall@10 从 E5 到 Rerank(top20) 提升了 0.0226，而从 Rerank(top20) 到 Rerank(top50) 仅进一步提升 0.0235；MRR@10 则从 0.4116 提升到 0.4637 后，又仅进一步提升到 0.4683。这表明随着重排深度增加，系统性能仍能持续优化，但其收益呈现出一定的边际递减趋势。换言之，前 20 个候选文献已经包含了大量高价值候选，继续扩大到前 50 个候选虽然仍有帮助，但额外收益相对有限。
分组结果进一步表明，不同类型查询对重排深度的敏感性并不一致。对于 inline_acl 查询，Rerank(top20) 已经能够显著提升 MRR@10 和 MRR@100，而扩大到 top50 后，MRR 虽然继续小幅上升，但 Recall@10 和 Hit@10 反而略有下降。这说明对于此类查询，更深的重排并不一定带来更好的 top10 覆盖效果，其主要收益仍体现在前列排序细化上。对于 inline_nonacl 查询，Rerank(top50) 与 Rerank(top20) 的差异较小，整体上 top50 仅带来非常有限的额外改进，表明这类查询对重排深度的扩展并不十分敏感。
相比之下，manual_acl 和 manual_iclr 两组对更深的重排范围表现出更明显的收益。在 manual_acl 组中，Recall@10 从 E5 的 0.6194 提升到 Rerank(top20) 的 0.6710，并进一步提升到 Rerank(top50) 的 0.7032；Hit@10 和 MRR 指标也呈现出相同趋势。在 manual_iclr 组中，这种现象更加突出：Recall@10 从 0.6813 提升到 0.7473，并进一步提升到 0.8242；MRR@10 则从 0.5085 提升到 0.6107，再进一步提升到 0.6320。可见，对于表达更明确、主题更集中、语义边界更清晰的人工构造查询，扩大重排深度能够持续带来明显收益，说明更多潜在相关文献在 top20 之外、top50 之内被重新排序到更靠前位置。
综合来看，重排深度的扩展对系统总体性能具有正向作用，但这种作用并非在所有查询类型上都同样显著。对于 inline_acl 和 inline_nonacl，top20 已经能够捕获大部分重排收益，继续扩大到 top50 的额外提升有限；而对于 manual_acl 和 manual_iclr，top50 明显优于 top20，表明更深的候选重排对于此类查询更加必要。总体上，E5 + Rerank(top50) 在本文所有实验设置中取得了最优结果，因此可以将其视为当前实验条件下的最佳检索方案。

本节通过对比 Rerank(top20) 与 Rerank(top50)，分析了重排深度对检索效果的影响。实验表明，扩大重排范围能够进一步提升系统前排排序质量，但收益存在边际递减现象。对于人工构造查询，top50 的提升更加明显；对于 inline 查询，top20 已经能够获得大部分收益。综合总体结果与分组结果，本文最终选择 E5 + Rerank(top50) 作为重排阶段的最优配置。

X.X.X 效率对比与结果权衡分析
除了检索效果之外，第二阶段重排方法在实际应用中的计算开销同样值得关注。由于 CrossEncoder 需要对查询与候选文献逐对进行相关性建模，其计算复杂度明显高于第一阶段的向量检索。因此，在重排深度逐渐增加的情况下，系统性能提升是否能够覆盖其额外开销，是需要进一步分析的问题。基于此，本文对 E5、E5 + Rerank(top20)、E5 + Rerank(top50) 和 E5 + Rerank(top100) 四种设置进行了效果与效率的综合比较。
从实验结果来看，随着重排深度从 top20 增加到 top50，再进一步扩大到 top100，系统在部分指标上持续提升，但计算时间也显著增加。整体而言，原始 E5 的 Recall@10、Hit@10 和 MRR@10 分别为 0.5827、0.5963 和 0.4116；在引入 Rerank(top20) 后，这些指标提升至 0.6053、0.6198 和 0.4637；当重排深度扩展到 top50 时，Recall@10 和 Hit@10 进一步提高到 0.6288 和 0.6399，MRR@10 也达到最高值 0.4683；继续扩大到 top100 后，Recall@10 和 Hit@10 分别进一步上升到 0.6321 和 0.6432，但 MRR@10 和 MRR@100 反而下降到 0.4561 和 0.4622。与此同时，运行时间则从 top20 的约 59 分钟，增加到 top50 的约 1 小时 59 分钟，再增加到 top100 的约 3 小时 40 分钟。
这一结果说明，重排深度越大，并不意味着所有指标都会持续提升。具体而言，top100 在 Recall@10 和 Hit@10 上优于 top50，说明更大的重排范围有助于将更多相关文献提前到前 10 个结果中；但 top50 在 MRR@10 和 MRR@100 上优于 top100，说明其更有利于将首篇相关文献推到更靠前的位置。换言之，top100 更偏向于提升前排结果中的相关文献覆盖率，而 top50 更偏向于优化首个相关文献的平均排序位置。对于以学术检索为目标的任务而言，这两类收益都具有意义，但其关注重点并不完全相同。
从效率角度分析，top20 已经能够在相对较低的计算成本下显著提升系统性能，是一种性价比较高的重排配置；top50 虽然耗时进一步增加，但在 Recall@10、Hit@10、MRR@10 和 MRR@100 上取得了更均衡的提升，因此可视为效果与成本之间较好的折中方案；top100 则需要最高的计算开销，虽然在 Recall@10 和 Hit@10 上达到最优，但其 MRR 指标反而低于 top50，说明进一步扩大重排范围后，收益开始出现不稳定现象。总体来看，随着重排深度不断扩大，系统性能的提升呈现出明显的边际收益递减特征，而计算代价却持续线性上升。
因此，若从“综合检索质量”角度出发，特别是考虑前排排序的稳定性与平均首个相关文献位置，E5 + Rerank(top50) 更适合作为本文实验中的最终推荐方案；若更加关注前 10 个结果中相关文献的覆盖能力，则 E5 + Rerank(top100) 在 Recall@10 和 Hit@10 上具有一定优势。结合学术检索场景中用户通常更关注前几条结果的排序质量，以及计算成本的现实约束，本文最终认为 top50 是效果与效率之间更合理的折中选择。
表后总结段（可接在表格后）
综合效率与效果对比结果可知，第二阶段重排能够显著改善 E5 的前排检索质量，但重排深度的增加并非总能带来稳定收益。top20 已经能够取得明显提升，top50 在多项关键指标上进一步达到最佳平衡，而 top100 虽然在 Recall@10 和 Hit@10 上表现最优，但其 MRR 指标有所回落，且耗时显著增加。由此可见，在本文实验设置下，E5 + Rerank(top50) 更适合作为最终检索方案。

4.X 端到端原型系统实现
在完成检索与重排实验之后，本文进一步实现了一个面向科学文献问答场景的最小端到端 RAG 原型系统，以验证前述方法在实际问答流程中的可部署性与可运行性。该原型系统围绕“用户问题输入—查询理解—文献检索—文档重排—上下文构建—回答生成—引用展示”的完整流程展开设计，在不破坏现有检索评测代码的前提下，采用模块化方式新增系统实现代码，并将相关文件统一组织在 rag/ 目录下。系统整体流程如图所示，可表示为：question → query understanding → E5 retrieval → rerank(top50) → context building → answer generation → citations。
在系统实现层面，本文遵循“尽量复用已有能力、尽量减少对原实验代码侵入”的原则。首先，在检索阶段，系统直接复用已有的 E5 检索能力，避免重新实现文献向量召回逻辑；在重排阶段，系统基于本地 CrossEncoder 重排方案完成前 top50 候选文献的精排，以继承前文实验中验证有效的主方案 E5 + rerank(top50)。考虑到原始检索与重排脚本主要面向离线实验设计，不完全适合在端到端问答流程中直接调用，因此本文在 rag/ 目录下对原有能力进行了轻量封装，使其能够以函数化、模块化方式被主流程调用，同时保证原有 eval/ 下的实验脚本、评测脚本和分析代码保持不变。通过这种方式，系统既能共享既有实验成果，又能避免因大规模修改原项目结构而引入新的不稳定因素。
为提升系统可维护性和后续扩展能力，端到端原型采用模块化结构实现，主要包括查询理解模块、检索与重排封装模块、上下文构建模块、回答生成模块以及主调度入口模块。查询理解模块负责对用户输入问题进行轻量分析和改写，当前支持 original 和 keywords 两种模式。其中，original 模式直接保留原始问题表达，keywords 模式则从原问题中提取更聚焦的关键词短语，用于改善文献召回效果。该模块的设计重点不在于复杂训练，而在于以较低实现成本提升检索意图表达质量，并为后续实验对比提供可控变量。
检索与重排封装模块负责将已有 E5 检索能力与本地重排模型串联起来。系统首先利用 E5 在已有文献索引中召回前 top_k 篇候选文献，然后调用本地重排模型对前 rerank_top_k 篇候选进行细粒度打分与排序，其余文献则保持原始顺序不变。该设计与前文重排实验保持一致，能够保证系统实现与实验结论的统一性。同时，为确保原型系统在环境不完整时仍可联调，系统还支持在缺少完整索引时回退到本地小规模样例语料进行测试，从而降低开发和调试成本。
上下文构建模块主要负责将重排后的文献结果组织成可供回答生成模块使用的上下文表示。当前实现中，本文设计了 plain 与 structured 两种策略。plain 策略直接拼接候选文献的标题与摘要信息，构造连续文本上下文；structured 策略则进一步保留文献编号、标题、摘要、排序位置与分数字段，并按 [D1]、[D2] 等形式组织证据。为避免上下文过长对系统运行造成影响，模块同时支持对单篇文献长度进行截断控制。该设计不仅有利于后续实验中对不同上下文增强策略进行比较，也为未来接入真实大模型时实现更稳定的引用对齐和证据追踪提供了基础。
回答生成模块当前采用可替换后端设计，以适应不同阶段的系统开发需求。在当前原型阶段，由于系统实现重点在于验证检索增强链路与上下文组织方式，因此回答生成优先采用 mock 后端。该后端基于已构建上下文生成模板化回答，并尽量显式引用文献编号，如 [D1]、[D2] 等，以体现科学文献问答系统的可解释性特征。与此同时，系统在实现时预留了 local 后端接口，使得后续可在不重构主流程的前提下，直接接入本地生成模型或外部 API 作为真实回答模块。也就是说，当前实现虽然在回答生成能力上采用了轻量化方案，但整体架构已经为后续增强留出了清晰接口。
主入口模块 run_rag_demo.py 负责串联上述各功能模块，并提供统一的命令行参数接口。用户可以通过命令行输入问题，并灵活配置查询理解模式、上下文策略、回答后端、召回文献数量和重排深度等关键参数。系统运行后，能够依次输出原始问题、查询理解结果、初始检索结果、重排后结果、上下文内容、最终回答和引用列表，从而为调试、分析和论文展示提供完整可见的中间过程。这种“显式展示中间状态”的实现方式不仅有助于系统开发过程中的问题定位，也强化了原型系统的可解释性，使研究者能够观察不同模块设置对最终输出的影响。
从工程实现角度看，本文所实现的端到端原型具有三个特点。首先，系统复用了前期已验证有效的检索与重排主方案，保证了系统实现与实验结论的一致性。其次，系统采用低侵入式扩展方法，将新增功能集中在 rag/ 目录中，避免破坏原有实验框架，便于后续维护与迭代。最后，系统在回答生成环节采用了“先闭环、后增强”的设计思路，即先用轻量 mock 模块验证问答链路的完整性，再为未来接入真实生成模型预留扩展接口。这种实现路径符合毕业设计阶段“先验证可行性，再逐步增强能力”的总体要求。
综合来看，本文完成的端到端原型系统虽然仍属于最小可运行版本，但已经具备科学文献 RAG 系统的基本要素：能够理解用户问题、完成文献召回与重排、组织证据上下文，并生成带引用的回答结果。该原型的实现不仅验证了前期检索增强方法的工程可落地性，也为后续开展查询理解策略比较、上下文增强实验以及小规模问答评测奠定了系统基础。

4.X 端到端原型实验结果分析
在完成 BM25、E5 检索及 E5 + rerank(top50) 重排实验的基础上，本文进一步搭建了面向科学文献问答的最小端到端 RAG 原型系统，以验证所提出方法在真实问答流程中的可用性。该原型系统实现了从用户问题输入、查询理解、文献检索、文档重排、上下文构建到回答生成与引用展示的完整闭环，主流程为：question → query understanding → E5 retrieval → rerank(top50) → context building → answer generation → citations。其中，检索主干采用已验证有效的 E5 模型，重排阶段采用本地 CrossEncoder 重排模型，回答生成阶段暂采用 mock 方式模拟基于证据的回答输出，以便在不引入额外生成模型变量的情况下，优先验证系统链路的完整性与模块设计的合理性。
从原型系统运行结果来看，当前方案已经能够在真实索引和本地重排模型支持下稳定运行。系统能够接收自然语言问题，完成查询理解，并基于检索与重排结果构建上下文，最终输出带有文献引用标记的回答结果。实验表明，所设计的端到端流程不存在明显的模块断裂问题，各阶段输入输出关系清晰，说明本文前期完成的检索与重排实验能够较自然地过渡到完整的科学文献问答场景中。这一结果表明，本文提出的系统不仅能够在离线检索指标上取得较好表现，也具备进一步演化为可交互学术问答系统的实现基础。
在查询理解模块上，本文比较了 original 与 keywords 两种方式的效果。以“Are there any research papers on methods to compress large-scale language models?” 为测试问题时，original 模式直接保留原始自然语言问题，而 keywords 模式则将问题压缩为更聚焦的检索表达，并显式提取关键词。实验结果显示，keywords 模式在初始召回阶段得到的文献结果更集中于“语言模型压缩方法”这一核心主题，例如低秩分解、矩阵分解、剪枝与压缩表示等方向；相较之下，original 模式虽然也能召回相关文献，但更容易引入与“大规模语言模型”相关但主题更宽泛的候选结果。进一步观察重排后的前列文献可以发现，keywords 模式下的前排结果与问题意图一致性更高，最终回答也更接近对“压缩方法类型”的总结，而不是围绕某一具体技术路线进行展开。这说明对于方法型学术问题，关键词化的查询理解策略有助于减少自然语言问句噪声，提高检索结果与最终回答的主题聚焦能力。
在上下文增强策略方面，本文对 plain 与 structured 两种上下文构建方式进行了对比。plain 策略主要采用直接拼接候选文献标题与摘要的方式构建上下文，而 structured 策略则显式保留文献编号、标题、摘要、排序位置和分数等结构化信息。实验结果表明，在当前 mock 回答后端下，两种策略生成的最终回答内容差异并不显著，说明在轻量回答模块条件下，最终输出主要受检索与重排结果质量驱动，而对上下文组织形式的敏感性相对有限。然而，从上下文展示形式来看，structured 策略使不同文献证据之间的边界更加清晰，有利于回答中的引用对齐与证据追踪，也更符合科学文献问答系统对于可解释性的要求。因此，尽管其在当前轻量生成阶段尚未带来明显的答案质量提升，structured 策略依然在可解释性与后续扩展性方面表现更优，更适合作为当前原型系统的默认上下文增强方案。
综合上述实验结果可以得到以下结论。首先，基于 E5 + rerank(top50) 的检索主干能够有效支撑端到端 RAG 原型系统运行，验证了前文检索与重排实验结论在问答场景中的可迁移性。其次，在查询理解模块中，keywords 相较 original 更适合作为当前系统的默认配置，其优势主要体现在降低问句噪声、增强主题聚焦和改善前排证据质量上。再次，在上下文构建模块中，structured 策略虽然在 mock 回答阶段未显著提高答案内容质量，但在证据组织、引用展示和可解释性方面具有明显优势。基于这些结果，本文当前阶段的端到端原型主方案可确定为：keywords query understanding + E5 retrieval + rerank(top50) + structured context + mock answer。
需要说明的是，当前原型系统中的回答生成模块仍采用 mock 方式，主要目的是验证检索增强链路与上下文组织策略的可行性，而非评估真实大模型的最终生成能力。因此，当前实验结论更适用于系统设计与模块有效性验证，而不代表完整生成式学术问答系统的最终上限。后续工作中，可在保持当前检索与上下文增强框架不变的前提下，引入真实生成模型，对 plain 与 structured 上下文在回答质量、引用准确性和可解释性方面的差异进行进一步验证。同时，还可基于更多问题样本构建小规模问答评测集，对查询理解策略和上下文增强策略开展更系统的定量分析。

4.X 查询理解模块设计与实现
在科学文献问答场景中，用户输入通常以自然语言问题形式出现，具有表达灵活、语义完整但检索噪声较多的特点。与传统关键词检索不同，自然语言问题往往包含大量功能性成分，如疑问表达、语气结构和非核心修饰语，这些内容虽然对人类理解问题有帮助，但未必有利于检索模型准确捕捉问题的核心学术意图。因此，在端到端 RAG 系统中，仅将原始问题直接送入检索模块，容易导致召回结果主题分散，进而影响后续重排与回答生成质量。基于这一考虑，本文在已有检索与重排框架基础上，设计并实现了一个轻量查询理解模块，用于在用户问题进入检索阶段之前，对其进行规范化处理与意图压缩表示。
本文所实现的查询理解模块遵循“轻量、可解释、低成本、易集成”的设计原则。一方面，本科毕业设计阶段不宜引入复杂的训练式查询改写模型，否则会显著增加额外数据准备、参数训练与系统调试成本；另一方面，查询理解模块应能够与已有 E5 检索主干自然衔接，并保留足够强的可解释性，便于分析其对检索结果的影响。因此，本文并未直接复现复杂的生成式 query rewriting 方法，而是面向科学文献问答场景，设计了两种可控的查询理解模式：original 与 keywords。其中，original 模式直接保留原始自然语言问题，用作基线输入；keywords 模式则从原始问题中提取更具检索意义的关键词或短语表达，用于弱化问句结构中的噪声信息，增强问题核心主题的显式表达。
从实现方式上看，查询理解模块接收用户输入问题后，首先保留原始问题文本作为 original_query，以便后续输出与分析。在 original 模式下，系统直接将原始问题作为检索输入；在 keywords 模式下，系统通过轻量规则方法对问题进行处理，包括去除疑问表达、过滤部分非核心功能词、保留学术实体和主题相关关键词，并将处理后的结果重新组织为更紧凑的检索表达。同时，模块还输出一个关键词列表，用于辅助调试与结果分析。通过这种设计，系统能够显式展示“原问题—压缩表达—关键词集合”之间的对应关系，从而保证查询理解过程本身具有较强可解释性。
本文之所以采用关键词化查询理解策略，主要基于以下考虑。首先，科学文献检索任务的目标通常不是复现用户问题的完整表面表达，而是尽可能准确地提取其学术主题和研究意图。例如，当用户提出“Are there any research papers on methods to compress large-scale language models?”这类问题时，真正决定文献检索结果的核心信息并不是疑问句式本身，而是“compress”、“large-scale language models”、“methods”等关键词及其组合关系。其次，关键词化表达更符合文献检索模型的召回特征，能够使问题表示向“研究主题”而非“口语问题”靠拢，从而提高候选文献的主题集中度。最后，该策略实现简单，不依赖额外标注数据和训练过程，适合作为原型系统中的查询理解起点，也便于后续与更复杂的改写方法进行对比。
从系统集成角度看，查询理解模块位于端到端原型的最前端，是连接用户问题与检索模块的关键中间层。主流程中，系统首先接收用户输入问题，然后调用查询理解模块生成对应的查询表示，再将该表示送入 E5 检索模块执行初始召回。由于该模块输出的是更适合文献检索的表达形式，因此它对后续检索结果质量具有直接影响。与此同时，模块还将原始问题、改写结果与关键词列表一并输出，使系统能够在调试与实验分析阶段直观观察不同查询模式下的行为差异。这种实现方式使查询理解不仅是一个“内部预处理步骤”，也成为一个可以独立分析、可进行消融实验的系统模块。
在实验验证中，本文以方法型学术问题为例，对 original 与 keywords 两种查询理解模式进行了对比。结果表明，相较于直接使用原始自然语言问题进行检索，关键词化后的查询表达能够更有效地减少问句形式带来的干扰，使初始召回结果更加集中于问题核心主题。在 E5 + rerank(top50) 主方案下，keywords 模式下的前列文献更聚焦于低秩分解、矩阵分解、剪枝与压缩表示等模型压缩方法，而 original 模式则更容易召回一些与大规模语言模型相关但主题分散的文献。由此可见，轻量关键词化查询理解虽然不属于复杂的算法创新，但作为一种面向学术问答场景的系统级增强策略，能够在不增加训练成本的前提下提升检索聚焦能力和回答主题一致性。
综合来看，本文设计与实现的查询理解模块并非对已有复杂查询改写方法的直接复现，而是结合科学文献 RAG 场景需求，在现有 LitSearch 检索与重排框架基础上新增的一层轻量扩展。其主要贡献在于：将查询理解作为独立模块纳入端到端科学文献问答系统设计，提出了基于关键词压缩表达的轻量实现方案，并通过端到端原型实验验证了其对方法型问题检索效果的正向作用。该模块的实现为后续进一步引入更复杂的 query rewrite 方法、实体增强方法或面向不同问题类型的自适应查询策略奠定了基础。
